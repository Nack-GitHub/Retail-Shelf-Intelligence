# OSA % และ "ชั้นที่ N · ตำแหน่ง…" คิดมาจากอะไร

เอกสารนี้อธิบาย **วิธีคำนวณ** ตัวเลขสองอย่างที่ผู้ใช้เห็นบ่อยที่สุด — OSA เป็น
เปอร์เซ็นต์ และป้ายบอกตำแหน่งช่องว่าง — ให้คนที่ไม่ได้อ่านโค้ดตอบคำถาม
"เลขนี้มาจากไหน" ได้

ถ้ากำลังหาว่า OSA % **แต่ละจอ** หมายถึงช่วงเวลาไหน (ภาพใบเดียว / ทั้งการเข้าร้าน /
ล่าสุดของร้าน) นั่นคนละเรื่องกัน อยู่ที่ [ui.md §1.6](ui.md#16-osa--บนหน้าจอ--ห้าตัวเลข-ไม่ใช่ตัวเดียว)

ต้นทางเดียวของทุกอย่างในเอกสารนี้คือ
[`backend/app/services/shelf_analysis.py`](../backend/app/services/shelf_analysis.py)
ค่าคงที่ทุกตัวมาจาก [`backend/app/core/config.py`](../backend/app/core/config.py)
ไม่มีที่อื่น

---

## 1. หลักการ: OSA วัดจาก **พื้นที่** ไม่ใช่จำนวนชิ้น

> `osa_score = 1 − (พื้นที่ช่องว่าง ÷ พื้นที่ชั้นวางที่มองเห็น)`

ระบบ **ไม่นับ** ว่าชั้นวางควรมีสินค้ากี่ชิ้นแล้วขาดไปกี่ชิ้น เพราะการนับแบบนั้น
ต้องรู้ planogram ที่ถูกต้องของทุกร้าน ซึ่งเราไม่มี และเวลาโมเดลมองไม่เห็นสินค้า
บางชิ้น (แสงสะท้อน มีคนยืนบัง) การนับจะเพี้ยนทันที

การวัดด้วย **สัดส่วนพื้นที่** เสื่อมสภาพอย่างนุ่มนวลกว่า — มองไม่เห็นบางส่วนของ
ชั้นวาง ก็แค่ตัดส่วนนั้นออกจากทั้งเศษและส่วน ผลลัพธ์ยังใช้ได้

**ผลที่ตามมาที่ต้องรู้:** ช่องว่างกว้าง 1 ช่องกินคะแนนมากกว่าช่องว่างแคบ 2 ช่อง
ตัวเลขนี้จึงตอบว่า "ชั้นวางโล่งแค่ไหนเมื่อลูกค้ามอง" ไม่ได้ตอบว่า "ขาดกี่ SKU"
จำนวน SKU ที่ขาดคือ `findings` ซึ่งเป็นคนละช่องบนหน้าจอ

## 2. ขั้นตอนการคำนวณ

โมเดลคืนมาแค่ bounding box + `semantic_type` (`PRODUCT` / `GAP` / `PRICE_TAG` /
`PROMO_TAG`) ML service **ไม่รู้จักคำว่า OSA** — กฎธุรกิจทั้งหมดอยู่ฝั่ง backend

### ขั้น 1 — กรองด้วย confidence

ทิ้ง detection ที่ `confidence < min_confidence` (**0.35**)
ตัวที่รอดแต่ยังต่ำกว่า `low_confidence_threshold` (**0.55**) ถูกทำเครื่องหมาย
`is_low_confidence` และ UI จะขึ้นว่า "ต้องตรวจสอบ" แทนที่จะยืนยันว่าเป็นช่องว่าง

### ขั้น 2 — จัดกลุ่มเป็นแถว (row clustering)

เรียง detection ตาม `center_y` แล้วตัดแถวใหม่ทุกครั้งที่ระยะห่างไปยังกล่องถัดไป
เกิน tolerance

```
tolerance = row_tolerance_ratio (0.6) × median(ความสูงของกล่อง PRODUCT/GAP)
```

tolerance ผูกกับความสูงกล่อง ไม่ใช่ค่าพิกเซลตายตัว กฎเดียวกันจึงใช้ได้ทั้งกับ
ภาพโคลสอัพชั้นเดียวและภาพกว้างทั้งตู้

**เฉพาะ `PRODUCT` กับ `GAP` เท่านั้นที่กำหนดว่าแถวอยู่ตรงไหน** ป้ายราคาไม่นับ
ด้วยเหตุผลสองข้อที่เจอจากภาพจริงทั้งคู่ — รางป้ายราคาแขวนอยู่ **ใต้** สินค้าที่มันติดราคาให้
และอยู่นอกช่วงความสูงของสินค้าแถวนั้น ถ้าเอามารวม ชั้นวางจริง 1 ชั้นจะกลายเป็น 2 แถว
และเลขชั้นทุกชั้นที่อยู่ต่ำกว่านั้นจะเกินความจริงทั้งหมด · อีกข้อคือกล่องป้ายราคาสูง
ประมาณ ¼ ของกล่องสินค้า มันจึงดึง median ลงจน tolerance เล็กเกินไปและทำให้แถวจริง
แตกเพิ่มอีก

### ขั้น 2.5 — ผูกป้ายราคาเข้ากับแถว

หลังได้แถวแล้วค่อยเอา `PRICE_TAG` / `PROMO_TAG` ไปแปะเข้าแถว โดยยึดหลัก
**"ป้ายเป็นของชั้นที่อยู่เหนือมัน"** เพราะรางป้ายติดอยู่ที่ขอบหน้าของแผ่นชั้น
สินค้าที่มันติดราคาให้คือสินค้าที่ *ยืนอยู่บนแผ่นนั้น* ซึ่งอยู่เหนือราง
(ถ้าเลือก "แถวที่ใกล้ที่สุด" แทน จะได้คำตอบผิดประมาณครึ่งหนึ่ง เพราะระยะจากราง
ไปแถวบนกับแถวล่างมักพอ ๆ กัน) ป้ายที่อยู่เหนือทุกแถว เช่นป้ายหัวตู้ ถือเป็นชั้นที่ 1

ขั้นนี้มีผลกับการแสดงผลอย่างเดียว ป้ายไม่มีพื้นที่ชั้นวาง จึงขยับ OSA ไม่ได้

### ขั้น 3 — วัดพื้นที่รายแถว

ในแต่ละแถว รวมพื้นที่แยกสองกอง โดยนับเฉพาะ `PRODUCT` กับ `GAP`

**`PRICE_TAG` และ `PROMO_TAG` ไม่ถูกนับทั้งเศษและส่วน** — ป้ายอยู่ที่ขอบชั้น
ไม่ใช่พื้นที่วางสินค้า ถ้านับเข้าไปในตัวหาร ทุกชั้นวางจะดูเต็มกว่าความจริง

### ขั้น 4 — สรุปทั้งภาพ

```
shelf_area = Σ product_area + Σ gap_area      (ทุกแถวรวมกัน)
gap_ratio  = Σ gap_area ÷ shelf_area
osa_score  = 1 − gap_ratio                    (0.0–1.0)
```

จัดสถานะจากเกณฑ์ใน config:

| osa_score | สถานะ |
| :-- | :-- |
| `< 0.75` (`critical_threshold`) | **CRITICAL** |
| `< 0.90` (`low_threshold`) | **LOW** |
| ที่เหลือ | **OK** |

เกณฑ์ชุดนี้ฝั่งเว็บ mirror ไว้ที่ `frontend/src/lib/osa.ts` และมีเทสต์
`backend/tests/unit/test_osa_thresholds_contract.py` คอยจับถ้าสองฝั่งไม่ตรงกัน

### ขั้น 5 — สร้าง finding ของแต่ละช่องว่าง

detection ที่เป็น `GAP` ทุกตัวกลายเป็น 1 finding พร้อมป้ายตำแหน่ง (ดูหัวข้อ 4)
เรียงตาม `(ชั้น, center_x)` — บนลงล่าง แล้วซ้ายไปขวาในแต่ละชั้น ให้ลำดับงาน
เดินตามที่พนักงานเดินจริง

> เรียงตาม**ข้อความ**ป้ายไม่ได้ เพราะ Python เรียงสตริงไทยตาม code point จะได้
> กลาง → ขวา → ซ้าย คือยื่นกลางชั้นให้ก่อนหัวชั้นด้านซ้ายเสมอ
> ฝั่ง DB ก็ต้อง `join` ตาราง `detections` แล้วเรียงด้วย `bbox_x` ให้ตรงกัน

| ชั้น | หน่วย |

## 4. "ชั้นที่ 4 · ตำแหน่งกลาง" มาจากอะไร

ป้ายนี้สร้างจาก **เรขาคณิตของภาพล้วน ๆ** ไม่ได้อ่านจาก planogram, ป้ายชั้น
หรือข้อมูลตู้ใด ๆ ทั้งสิ้น

**"ชั้นที่ N"** = ลำดับของ cluster จากขั้น 2 นับ **จากบนลงล่าง** เริ่มที่ 1

**"ตำแหน่งซ้าย / กลาง / ขวา"** = `center_x` ของช่องว่างนั้นตกอยู่ในหนึ่งในสามส่วน
ของ **ความกว้างภาพ**

```python
third = min(int(center_x / (image_width / 3)), 2)
```

### สามข้อควรระวังเมื่ออ่านป้ายนี้

1. **เลขชั้นเป็นของ "รูปนั้น" ไม่ใช่ของตู้จริง** — ถ่ายเฉพาะครึ่งล่างของตู้
   ชั้นบนสุดในรูปก็ยังเป็น "ชั้นที่ 1" อยู่ดี ป้ายนี้ออกแบบมาให้พนักงานที่
   **ยืนอยู่หน้าชั้นวางและถือรูปนั้นอยู่** หาช่องว่างเจอใน 2 วินาที ไม่ได้
   ออกแบบมาให้อ้างอิงข้ามรูปหรือข้ามครั้งที่เข้าร้าน

2. **นับเฉพาะชั้นที่มีของ ป้ายราคาไม่กินเลขชั้น** — เลขที่เห็นคือจำนวนแผ่นชั้น
   ที่เห็นในรูป พนักงานนับตามด้วยตาได้ตรง ๆ (เหตุผลอยู่ในขั้น 2)

3. **"ซ้าย/กลาง/ขวา" อ้างอิงกรอบภาพ ไม่ใช่ตัวตู้** — ถ่ายเฉียงหรือถ่ายไม่เต็มตู้
   คำว่า "ขวา" คือขวาของรูป ไม่ใช่ขวาของชั้นวาง

### ตัวเลข "N หน้าร้าน" ที่อยู่ข้างป้าย **ไม่ได้มาจากรูป**

บนหน้ารายการงานจะเห็นเป็น `ชั้นที่ 4 · ตำแหน่งกลาง · 2 หน้าร้าน` — ส่วนสุดท้าย
คนละต้นทางกับสองส่วนแรกทั้งหมด

ชื่อ SKU กับจำนวนหน้าร้านมาจาก [`planogram.json`](../backend/app/services/planogram.json)
เปิดตารางด้วย **ตำแหน่งของช่องว่าง** (`(ชั้น × 7 + ลำดับ) % จำนวน SKU`) ไม่ได้อ่านคลาส
ที่โมเดลตรวจเจอข้าง ๆ ช่องนั้น และ `facings` คือค่าเฉลี่ยจำนวนกล่องของ SKU นั้น
ต่อภาพทั้ง dataset ไม่ใช่ความกว้างของช่องว่างที่วัดได้จากรูปใบนี้

อ่านว่า "ชั้นวางบอกว่าตรงนี้ควรมีอะไรอยู่" ไม่ใช่ "ระบบเห็นว่าหายไปกี่กล่อง"
รายละเอียดว่าไฟล์นี้สร้างมาอย่างไรอยู่ที่ [running.md](running.md#ชื่อสินค้าที่ระบบบอกให้เติม)

## 5. กรณีที่ระบบ **ไม่ยอม** ให้ค่า OSA

ทั้งสองกรณีนี้โยน `NoShelfDetectedError` และงานวิเคราะห์จบด้วยสถานะ FAILED
พร้อมข้อความให้ถ่ายใหม่ — **ไม่ใช่** รายงานเป็น 0% หรือ 100%

| สถานการณ์ | ทำไมถึงไม่ให้ค่า |
| :-- | :-- |
| ไม่มี detection ใดผ่าน confidence floor | "ไม่พบช่องว่าง" กับ "มองไม่เห็นอะไรเลย" เป็นคนละคำตอบ ถ้าตอบเป็น 100% เทรนด์ทุกเส้นที่สร้างต่อจากข้อมูลนี้จะเสียหมด |
| เห็นแต่ป้ายราคา (ไม่มีกล่อง `PRODUCT`/`GAP` เลย) | เห็นขอบชั้นแต่ไม่เห็นว่ามีอะไรอยู่บนชั้น ตอบ 0% หรือ 100% ล้วนเป็นการแต่งเรื่อง |

## 6. ทำไมตัวเลขถึงไม่ขยับตอนติ๊กว่าเติมของแล้ว

OSA ขยับได้ทางเดียวคือ **มีภาพใหม่ถูกวิเคราะห์** การติ๊กงานว่าเติมแล้วไม่ทำให้
`osa_after` เปลี่ยน เพราะการประมาณค่าจากจำนวนงานที่ติ๊กจะอ่านสูงเกินจริงเสมอ
(มันแอบสมมติว่างานที่ติ๊กแล้วคืนพื้นที่ชั้นวางได้เต็มส่วน) และจะขัดกับตัวเลข
ที่ผู้จัดการเห็นบนเว็บสำหรับการเข้าร้านครั้งเดียวกัน

### วิธีรวบยอด "ก่อน" กับ "หลัง" ไม่สมมาตร — และตั้งใจให้เป็นแบบนั้น

| ค่า | รวบยอดอย่างไร | โค้ด |
| :-- | :-- | :-- |
| `visit.osa_before` | ภาพ `BEFORE` **ใบแรก**ของการเข้าร้านครั้งนี้ ภาพถัดมาไม่เขียนทับ | [`analysis_pipeline.py`](../backend/app/services/analysis_pipeline.py) (ตอนวิเคราะห์เสร็จ) |
| `visit.osa_after` | ภาพ `AFTER` **ใบล่าสุด**ของการเข้าร้านครั้งนี้ ภาพก่อนหน้าถูกแทนที่ | [`visits.py`](../backend/app/api/v1/visits.py) (ตอน checkout) |

**ทั้งคู่ไม่ใช่ค่าเฉลี่ย** — ยืนยันด้วยเทสต์
`test_the_two_figures_aggregate_differently_and_deliberately` และ
`test_retaking_an_after_photo_replaces_the_reading_it_corrects`
ใน `backend/tests/integration/test_golden_path.py`

เหตุผลของความไม่สมมาตร: **"ก่อน" คือสภาพที่พนักงานเดินเข้าไปเจอ** ภาพที่ถ่ายทีหลัง
เปลี่ยนอดีตไม่ได้ · **"หลัง" คือสภาพที่ทิ้งไว้** ซึ่งภาพที่ถ่ายทีหลังเป็นคำตอบที่
ใหม่กว่าเสมอ

ที่เลิกใช้ค่าเฉลี่ยเพราะการถ่ายซ้ำคือ **การแก้ไข** ไม่ใช่การเก็บตัวอย่างเพิ่ม
ภาพแรกเบลอหรือติดขอบเบย์ไม่ครบ แล้วถ่ายใหม่ — ถ้าเอามาเฉลี่ยกัน ภาพที่ทิ้งไปแล้ว
จะยังฉุดตัวเลขอยู่ และการถ่ายใหม่จะแก้ของเดิมได้ไม่หมด

**ลำดับ "ใบล่าสุด" วัดจากเวลาที่กดชัตเตอร์ (`captured_at`) ไม่ใช่เวลาที่แถวถูกเขียน**
เพราะคิวออฟไลน์ drain ตามลำดับที่ต่อเน็ตติด ไม่ใช่ลำดับที่ถ่าย
ถ้าภาพเดียวถูกวิเคราะห์ซ้ำหลายรอบ ใช้ `computed_at` ตัดสินว่ารอบไหนใหม่กว่า

**ผลที่ตามมาที่ต้องรู้:** เข้าร้านครั้งเดียวถ่ายหลายเบย์ "หลัง" จะเป็นค่าของ
**เบย์ที่ถ่ายทีหลังสุดเบย์เดียว** ไม่ใช่ภาพรวมทุกเบย์ (ส่วน "ก่อน" เป็นของเบย์แรก)
ตัวเลขคู่นี้จึงอ่านเป็น "ชั้นวางที่ลงมือทำดีขึ้นไหม" ได้ แต่ **อ่านเป็น OSA
ของทั้งร้านไม่ได้** — ตัวเลขระดับร้านคือ `store_risk.last_osa` และกราฟใน W1

ตารางว่า OSA % บนแต่ละจอคือค่าไหน อยู่ที่ [ui.md §1.6](ui.md#16-osa--บนหน้าจอ--ห้าตัวเลข-ไม่ใช่ตัวเดียว)
