# Web Admin (W1–W6) — ตัวเลขแต่ละตัวมาจากไหน กดอะไรได้จริงบ้าง

เอกสารนี้ตอบคำถามเดียว: **บนหน้าจอ Web Admin อะไรคือของจริง**

- ตัวเลขแต่ละช่องคำนวณจากอะไร ด้วยสูตรไหน อ่านจากตารางไหน
- อันไหนต่อกับฐานข้อมูลจริง อันไหนเป็นค่าที่อยู่แค่ในหน้าจอ
- ปุ่มไหนกดแล้วเกิดผลจริง ปุ่มไหนกดได้แต่ไม่ถูกบันทึก
- จุดที่ **คำบรรยายบนจอกับสิ่งที่โค้ดทำจริงยังไม่ตรงกัน** (§7)

เรื่องที่อยู่ที่อื่น: วิธีคำนวณ OSA ของภาพหนึ่งใบอยู่ที่ [osa.md](osa.md) ·
นิยามของ "OSA %" แต่ละจออยู่ที่ [ui.md §1.6](ui.md#16-osa--บนหน้าจอ--ห้าตัวเลข-ไม่ใช่ตัวเดียว) ·
สิ่งที่ยังไม่เปิดใช้ในรุ่นนี้สำหรับผู้ทดสอบอยู่ที่ [uat.md §3](uat.md#3-สิ่งที่ยังไม่เปิดใช้งานในรุ่นนี้)

## 0. สรุปสั้น ๆ ก่อน

| คำถาม | คำตอบ |
| :-- | :-- |
| **ภาพรวมพื้นที่ คำนวณถูกไหม** | สูตรถูกและอ่านจากข้อมูลจริงทั้งหมด · คำบรรยายใต้กราฟเคยเขียนว่า "ถ่วงน้ำหนักตามจำนวนร้าน" ซึ่งไม่ตรงกับ SQL — **แก้แล้ว** ตอนนี้บอกตรง ๆ ว่าเป็นค่าเฉลี่ยต่อ *ภาพ* และรวมภาพหลังเติมของด้วย (§2.4) |
| **แผนเส้นทางที่จัดไว้ mobile จะเรียงตามไหม** | **ไม่ตาม** ทั้งลำดับที่ลาก การตัดร้านออก และการกดอนุมัติ อยู่ใน state ของหน้าเว็บเท่านั้น ไม่เคยถูกส่งไปไหน · มือถือเรียกคนละ endpoint แล้วเรียงลำดับของตัวเองใหม่ (§3.4) **— ข้อนี้ยังเป็นแบบเดิม เพราะการทำให้แผนถึงมือพนักงานต้องมีตารางเก็บแผนและ endpoint ใหม่ ไม่ใช่การแก้หน้าจอ** |
| **สุขภาพของโมเดล แสดงถูกไหม** | ตัวเลขทุกตัวถูกและเป็นค่าที่วัดจริง (recall 0.7422 / precision 0.7480 / mAP 0.9065) · แบนเนอร์แดงเคยขัดกับหัวข้อของตัวเองเมื่อ `ML_CLIENT=http` — **แก้แล้ว** (§4.4) |
| **คิวตรวจภาพ ต่อข้อมูลจริงไหม กดได้จริงไหม** | ภาพ กรอบ เหตุผล และ confidence เป็นของจริงจากฐานข้อมูล · เลือก/กรองได้จริง · **กดดูภาพเต็มพร้อมกรอบได้แล้ว** และคิวมีทางจบแล้ว (finding ที่ถูกยืนยันจะออกจากคิว) · ปุ่ม "ทำเครื่องหมายว่าตรวจแล้ว" ยังซ่อนการ์ดในหน้าจอเท่านั้น (§5.4) |

> **สถานะเอกสาร** — รอบแก้ตาม §7 ทำไปแล้ว 10 จาก 10 ข้อ เนื้อหาทุกหัวข้อด้านล่างอัปเดตให้ตรงกับโค้ดปัจจุบันแล้ว
> รายการที่แก้ไปและที่ยังเหลืออยู่ที่ [§7](#7-สถานะการแก้ไข)

## 1. พื้นฐานที่ใช้ร่วมกันทุกหน้า

**สิทธิ์** — ทั้งสี่หน้าอยู่ใต้ [`/w/layout.tsx`](../frontend/src/app/w/layout.tsx) →
`AuthGate` → `WebShell` ฝั่ง API ทุก endpoint ผูก `require_roles(MANAGER, ADMIN, DATA)`
พนักงานภาคสนาม (REP) ที่หลุดเข้ามาจะเห็นหน้า "เฉพาะผู้จัดการและทีมข้อมูล" ไม่ใช่หน้าว่าง

**ตัวเลือกพื้นที่** — อยู่ใน sidebar ([`WebShell.tsx`](../frontend/src/components/web/WebShell.tsx))
ส่งผ่าน React context ไม่ใช่ query param เพื่อไม่ให้แต่ละหน้าตั้ง default ของตัวเอง
ค่าเริ่มต้นคือพื้นที่ของผู้ใช้เอง ทุกหน้าจะรอ `ready` ก่อนยิง request มิฉะนั้น dashboard
จะแวบเป็นตัวเลขทั้งประเทศหนึ่งครั้งก่อนเปลี่ยนเป็นพื้นที่ที่ถูกต้อง

> หน้า W5 และ W6 **ไม่ผูกกับพื้นที่** (โมเดลเป็นของทั้งระบบ) แต่ตัวเลือกพื้นที่ยังโชว์อยู่
> ใน sidebar และไม่มีผลอะไรบนสองหน้านั้น

**หน่วยของตัวเลข** — API พูดเป็นอัตราส่วน `0..1` เสมอ หน้าจอแสดง `0..100` เสมอ
การแปลงเกิดที่เดียวคือ `toPercent()` ใน [`lib/api/client.ts`](../frontend/src/lib/api/client.ts)
`null` ผ่านไปเป็น `null` — **"ไม่เคยวัด" ไม่ใช่ "0%"** และห้ามกลายเป็น 0% ที่จุดไหนก็ตาม

**สถานะการโหลด** — ทุกหน้าใช้ `useResource` + `LoadingBlock` / `ErrorBlock` ครบสามสถานะ
(กำลังโหลด / ล้มเหลวพร้อมปุ่มลองใหม่ / ไม่มีข้อมูล) ไม่มีหน้าไหนปล่อยจอขาว

**ไม่มี auto-refresh** — ทุกหน้าดึงข้อมูลตอนเปิดครั้งเดียว ตัวเลขคือ snapshot ณ ตอนเปิดหน้า
ต้องรีเฟรชเองถึงจะได้ค่าใหม่

**ข้อห้ามที่บังคับด้วยเทสต์** — ไม่มี endpoint ไหนใน W1–W6 ที่ group by / return `user_id`
บังคับด้วย `test_prohibitions.py` 14 ตัว รวมถึงตัวที่อ่าน source ของ `analytics.py` ตรง ๆ

## 2. W1 — ภาพรวมพื้นที่ (`/w`)

[`app/w/page.tsx`](../frontend/src/app/w/page.tsx) · API: [`analytics.py`](../backend/app/api/v1/analytics.py)

### 2.1 การ์ด KPI แถวบน

`GET /v1/analytics/kpis?days={28|84|182}&areaId=…`

การ์ดจะมีเฉพาะตัวที่ฐานข้อมูลตอบได้ **ถ้าคำนวณไม่ได้คือไม่มีการ์ดนั้น ไม่ใช่การ์ดที่แสดง 0**
(`ต้นทุนต่อการตรวจ` จึงไม่มีเลย เพราะระบบไม่มีข้อมูลต้นทุนอยู่ที่ไหนทั้งสิ้น)

| การ์ด | คำนวณจาก | เป้าหมาย |
| :-- | :-- | :-- |
| **OSA เฉลี่ยของพื้นที่** | `AVG(shelf_analyses.osa_score)` ของแถวที่ `computed_at` อยู่ในช่วง join capture → visit → store แล้วกรองด้วย `area_id` | 90% |
| **เวลาเฉลี่ยจากตรวจพบถึงเติมของสำเร็จ** | `AVG(tasks.completed_at − gap_findings.created_at)` เฉพาะงานที่ `status = FIXED` และ finding เกิดในช่วงนั้น | 30 นาที |
| **ร้านที่ตรวจใน N วันล่าสุด** | `COUNT(DISTINCT visits.store_id)` — **นับร้าน ไม่ใช่นับครั้ง** ร้านเดียวที่เข้า 40 ครั้งนับเป็น 1 | ไม่มีเป้า |

**ชิป +/− ข้างตัวเลข** เทียบกับ "ช่วงเวลาก่อนหน้าที่ยาวเท่ากัน" (28 วันเทียบ 28 วันก่อนหน้า
ไม่ใช่เทียบกับเวลาลอย ๆ) ถ้าไม่มีช่วงก่อนหน้าให้เทียบ API ส่ง `delta: null` แล้วชิป**หายไปทั้งชิป**
— ไม่ใช่แสดง 0 ซึ่งจะอ่านว่า "ทรงตัว" · `delta` เท่ากับ 0 พอดี = ทรงตัวจริง แสดงเป็นชิปเทาไม่มีลูกศร

**แถบเทียบเป้าหมาย** — KPI ที่ "ยิ่งมากยิ่งดี" ใช้ `value / target` · ที่ "ยิ่งน้อยยิ่งดี" (TTR)
ใช้ `target / value` กลับด้าน แถบจึงเต็มเมื่อทำได้ตามเป้าทั้งสองแบบ

### 2.2 กราฟแนวโน้ม OSA

`GET /v1/analytics/osa?days=…&areaId=…`

```sql
date_trunc('week', shelf_analyses.computed_at) AS bucket,
AVG(shelf_analyses.osa_score),
COUNT(DISTINCT visits.id)
```

จุดบนกราฟคือค่าเฉลี่ยรายสัปดาห์ · เส้นประแดงคือเป้า 90% (ค่าเดียวกับการ์ด OSA)
· **มีข้อมูลน้อยกว่า 2 สัปดาห์จะไม่วาดกราฟ** แต่ขึ้นข้อความแทน เพราะจุดเดียวไม่ใช่แนวโน้ม
การลากเส้นผ่านมันจะสื่อทิศทางที่ข้อมูลยืนยันไม่ได้

**สองข้อที่ต้องรู้ก่อนอ่านเส้นนี้ และตอนนี้เขียนอยู่บนหน้าจอแล้ว:**

1. `AVG()` เฉลี่ยต่อ **แถววิเคราะห์ = ต่อภาพ** ไม่ใช่ต่อร้าน ร้านที่ถ่าย 8 ภาพในสัปดาห์นั้น
   มีน้ำหนักเป็น 8 เท่าของร้านที่ถ่ายภาพเดียว
2. ค่าเฉลี่ยรวมทั้งภาพ **ก่อน** และ **หลัง** เติมของ ภาพ AFTER คะแนนสูงกว่าเสมอ

เส้นนี้จึงอ่านว่า *"ชั้นวางที่ถูกถ่ายในสัปดาห์นั้นเป็นอย่างไร"* ไม่ใช่ *"ร้านในพื้นที่โดยเฉลี่ยเป็นอย่างไร"*
— ประโยคนี้อยู่ใต้กราฟจริง ๆ ไม่ได้อยู่แค่ในเอกสารนี้

> **ทำไมไม่แก้ SQL ให้ถ่วงน้ำหนักตามร้านไปเลย** — การเปลี่ยนนิยามของ KPI ที่ผู้จัดการใช้ตัดสินใจ
> เป็นการตัดสินใจของ trade marketing ไม่ใช่ของคนแก้โค้ด และถ้าแก้เฉพาะกราฟ กราฟจะไม่ตรงกับ
> การ์ด OSA ที่ใช้ `AVG()` แบบเดียวกัน รอบนี้จึงแก้ให้ **หน้าจอพูดตรงกับสิ่งที่คำนวณ** ก่อน

### 2.3 ตาราง "ร้านที่ต้องเข้าดูแลก่อน"

`GET /v1/analytics/risk-ranking?areaId=…&limit=20` — ทั้งสามคอลัมน์มาจาก
[`repositories/store_risk.py`](../backend/app/repositories/store_risk.py) ซึ่งเป็น**แหล่งเดียวกัน**
กับที่หน้าเส้นทางของมือถือใช้ (จงใจรวมไว้ที่เดียว ไม่งั้นสองหน้าจะเถียงกันว่าร้านไหนแย่ที่สุด)

| คอลัมน์ | ที่มา |
| :-- | :-- |
| **OSA ล่าสุด** | `DISTINCT ON (store_id) … ORDER BY computed_at DESC` = แถววิเคราะห์**ล่าสุด**ของร้าน — ชั้นไหนก็ได้ เฟสไหนก็ได้ · จงใจไม่ใช้ `MAX()` เพราะ MAX ตอบว่า "ชั้นวางนี้เคยดูดีที่สุดแค่ไหน" ซึ่งเป็น 1.0 สำหรับร้านที่เคยเต็มสักครั้ง แล้วอันดับความเสี่ยงจะแบนหมด |
| บรรทัดใต้ OSA (`<OsaSource>`) | `lastOsaPhase` + `lastOsaAt` → "ก่อนเติมของ" / "หลังเติมของ" · บังคับตาม [ui.md §1.6 ข้อ 1](ui.md#16-osa--บนหน้าจอ--ห้าตัวเลข-ไม่ใช่ตัวเดียว) |
| **SKU ที่ขาดซ้ำ** | นับ `sku_code` ที่ถูกยืนยัน (`CONFIRMED`) ว่าขาด **ในการเข้าร้านมากกว่า 1 ครั้ง** — `HAVING COUNT(DISTINCT visit_id) > 1` คือหัวใจของการวัดนี้ ถ้านับ SKU ที่ขาดทั้งหมดแทน ตัวเลขจะโตตามขนาดชั้นวางและจำนวนครั้งที่เข้า และไม่มีวันลดลงแม้ร้านจะแก้ปัญหาแล้ว |
| **ตรวจครั้งล่าสุด** | `now − MAX(visits.checked_in_at)` เป็นจำนวนวันเต็ม |
| **ระดับความเสี่ยง** | สูตรด้านล่าง |

**สูตรความเสี่ยง** ([`services/risk.py`](../backend/app/services/risk.py) — ฟังก์ชันบริสุทธิ์ ไม่แตะ I/O):

```
risk_score = 0.55 × (1 − OSA ล่าสุด)              ← ไม่เคยวัด ใช้ 0.5
           + 0.30 × min(วันที่ไม่ได้เข้า ÷ 30, 1)   ← ไม่เคยเข้า ใช้ 30 วัน → 1.0
           + 0.15 × min(SKU ที่ขาดซ้ำ ÷ 10, 1)
```

| คะแนน | ระดับ |
| :-- | :-- |
| ≥ 0.55 | **สูง** |
| ≥ 0.35 | กลาง |
| < 0.35 | ต่ำ |

ผลที่ตั้งใจ: ร้านที่**ไม่เคยตรวจเลย**ได้ `0.55×0.5 + 0.30×1 = 0.575` → **เสี่ยงสูงทันที**
เพราะจุดประสงค์ของเส้นทางคือไปหาคำตอบ และ "ไม่มีข้อมูล" ไม่เท่ากับ "ไม่มีปัญหา"

### 2.4 สถานะของจุดที่เคยไม่ตรง

| เรื่อง | สถานะ |
| :-- | :-- |
| คำบรรยายกราฟอ้างว่าถ่วงน้ำหนักตามจำนวนร้าน | ✅ แก้แล้ว — เปลี่ยนเป็น "ค่าเฉลี่ยของทุกภาพที่วิเคราะห์ในสัปดาห์นั้น ทั้งก่อนและหลังเติมของ" |
| ไม่มีอะไรบอกว่ากราฟรวมภาพหลังเติมของ | ✅ แก้แล้ว — เพิ่มบรรทัดใต้กราฟอธิบายทั้งเรื่องน้ำหนักและเรื่องเฟส |
| ชิป "N ร้าน" คือจำนวนแถวที่ถูกจำกัดไว้ 20 | ✅ แก้แล้ว — ครบ 20 เมื่อไหร่ชิปจะเขียนว่า "20 ร้านที่เสี่ยงที่สุด" · จำนวนแถวส่งจากหน้าจอเป็น `RISK_ROW_LIMIT` ไม่ปล่อยให้เป็น default ของ API |
| ลิงก์ "ดูหลักการวัดผล" ชี้ไปหน้าเกณฑ์ของโมเดล | ✅ แก้แล้ว — เปลี่ยนข้อความเป็น "ดูสุขภาพของโมเดลที่ผลิตตัวเลขเหล่านี้" ให้ตรงกับปลายทาง |
| ชิป delta ของ KPI ที่ไม่ใช่ % ไม่มีหน่วย | ⏳ ยังเหลือ — ขึ้นว่า "3 · เทียบ 84 วันก่อนหน้า" โดยไม่บอกว่า 3 ร้านหรือ 3 นาที |

| เวลาในร้านรวม | บวกเฉพาะร้านที่**มีค่าที่วัดได้** ร้านที่เป็น `null` ถูกข้าม ไม่ใช่นับเป็น 0 · หัวข้อจะเปลี่ยนเป็น "(จาก 3/7 ร้านที่มีข้อมูล)" เองเมื่อไม่ครบ |
| ครอบคลุมร้านเสี่ยงสูง | `ร้านเสี่ยงสูงที่ยังอยู่ในแผน ÷ ร้านเสี่ยงสูงทั้งหมดในลิสต์` · ถ้าไม่มีร้านเสี่ยงสูงเลย = 100% (ไม่ใช่ 0% แล้วเตือนถึงร้านที่ไม่มีอยู่จริง) |

### 3.3 กดอะไรได้บ้าง

| ปุ่ม / การกระทำ | เกิดอะไรขึ้นจริง |
| :-- | :-- |
| สลับ "ตามความเสี่ยง / ตามวันที่ไม่ได้เข้า" | เรียงใหม่ในหน้าจอทันที (client-side) ไม่ยิง API ใหม่ · เกณฑ์ที่เลือกไว้ยังมีผลเมื่อข้อมูลโหลดใหม่ (เปลี่ยนพื้นที่ / กดลองใหม่) ปุ่มกับลำดับจึงไม่หลุดจากกัน |
| **ลากเพื่อจัดลำดับ** | ลากได้จริง แต่อยู่ใน `useState` เท่านั้น |
| "ตัดออก" / "ใส่กลับ" | อยู่ใน `useState` เท่านั้น |
| **"ทำเครื่องหมายว่าตรวจแล้ว"** | เปลี่ยน flag ในหน้าจอเป็นสีเขียว **ไม่มี API อยู่หลังปุ่มนี้** |

ทั้งหมดนี้เขียนบอกไว้ใต้ปุ่มแล้ว: *"ลำดับที่จัดไว้และการทำเครื่องหมายนี้ยังไม่ถูกบันทึก —
เป็นการดูตัวอย่างในหน้านี้เท่านั้น รีเฟรชแล้วจะกลับไปเป็นลำดับตามความเสี่ยง"*

> ไม่มีการเรียงตามระยะทางให้เลือก โดยตั้งใจ — แผนรายสัปดาห์ไม่มี "ตำแหน่งปัจจุบัน" ให้วัดระยะจาก

### 3.4 ❗ มือถือเรียงตามแผนนี้ไหม — **ไม่**

สองหน้านี้**ไม่ได้คุยกัน** มือถือเรียกคนละ endpoint แล้วเรียงลำดับของตัวเองใหม่ทุกครั้ง

| | เว็บ (W4) | มือถือ (S2) |
| :-- | :-- | :-- |
| Endpoint | `GET /v1/analytics/route-plan` | `GET /v1/routes/today` |
| การเรียง | `riskScore` มากไปน้อย · **เสมอกันแล้วลำดับไม่แน่นอน** (DB ไม่ได้ ORDER BY) | `(riskScore มากไปน้อย, ระยะทางน้อยไปมาก)` — **ตัดสินเสมอด้วยระยะทาง** |
| ขอบเขต | พื้นที่ที่เลือกจาก dropdown | พื้นที่ของ**บัญชีพนักงานที่ล็อกอิน** |
| จำนวน | สูงสุด 20 ร้าน | ทุกร้านในพื้นที่ ไม่จำกัด |
| ลำดับที่ผู้จัดการลาก | อยู่ในหน่วยความจำของเบราว์เซอร์ | **มองไม่เห็น** |
| ร้านที่ถูก "ตัดออก" | หายจากสรุป | **ยังขึ้นอยู่ในเส้นทางของพนักงานตามปกติ** |
| การกด "ตรวจแล้ว" | เปลี่ยนสีปุ่ม | **ไม่มีอะไรเกิดขึ้น** |

**สิ่งที่ทำให้สองจอ "ดูเหมือนตรงกัน"** คือทั้งคู่คำนวณจาก `store_risk` + `risk_score` ตัวเดียวกัน
ลำดับจึงพ้องกันโดยบังเอิญ ไม่ใช่เพราะแผนถูกส่งไป · ทันทีที่มีร้านคะแนนเสมอกัน
หรือเมื่อผู้จัดการลากสลับเอง สองจอจะไม่ตรงกันทันที

หมายเหตุอีกข้อ: `/v1/routes/today` คืน **ทุกร้านในพื้นที่** ไม่ใช่ "ร้านที่ถูกมอบหมายวันนี้"
— ระบบยังไม่มีตารางการมอบหมายงาน · และถ้าบัญชีพนักงานไม่มี `area_id` เงื่อนไขจะกลายเป็น
`Store.area_id == Store.area_id` ซึ่งคืนทุกร้านในระบบ

## 4. W5 — สุขภาพของโมเดล (`/w/model-health`)

[`app/w/model-health/page.tsx`](../frontend/src/app/w/model-health/page.tsx) ·
API: [`model_health.py`](../backend/app/api/v1/model_health.py) · `GET /v1/model/health?weeks=12`

### 4.1 การ์ดเกณฑ์ (gates)

อ่านจากคอลัมน์ `model_versions.metrics` ซึ่งเป็น **JSON ที่คัดลอกมาทั้งก้อน**จากไฟล์
`model/artifacts/<ชื่อโมเดล>/metrics.json` ตอน `make seed`
([`seed.py::_seed_model_versions`](../backend/app/db/seed.py)) — backend ไม่เคยคำนวณเมตริกเอง
และไม่เคย import ไลบรารี CV

การ์ดเหล่านี้เป็นของ **โมเดลที่กำลังให้บริการ** เสมอเมื่อโมเดลนั้นมีผลประเมิน
ถ้าโมเดลที่ active ไม่มี metrics (เช่นโหมด mock) หน้าจอจะถอยไปแสดงเวอร์ชันที่มีผลประเมินล่าสุด
**พร้อมเขียนกำกับไว้ตรง ๆ ว่าเกณฑ์ด้านล่างไม่ใช่ของโมเดลที่ให้บริการอยู่**

ค่าที่โชว์ตัวใหญ่ **ไม่ได้ parse มาจากข้อความ `detail`** แต่อ่านจากฟิลด์ตรง ๆ ผ่าน `GATE_VALUES`
(เคย parse จาก `detail` แล้วพอฝั่ง ML เปลี่ยนรูปแบบข้อความ ทุกการ์ดกลายเป็น "0.000 — ต่ำกว่าเกณฑ์"
อย่างมั่นใจ) · ส่วนตัวเลข **เกณฑ์** ยังตัดมาจาก `detail.split(" vs ")[1]` อยู่

ค่าปัจจุบันบนเครื่องนี้ (`shelf-product-yolo26l-960`, split = test, imgsz 960):

| เกณฑ์ | ต้องได้ | ได้จริง | |
| :-- | --: | --: | :-- |
| Recall — คลาสช่องว่าง | ≥ 0.90 | **0.7422** | ❌ |
| Precision — คลาสช่องว่าง | ≥ 0.85 | **0.7480** | ❌ |
| mAP@0.5 ทุกคลาส | ≥ 0.85 | 0.9065 | ✅ |

**ตัวเลขเหล่านี้คือของจริงที่วัดได้ และจงใจไม่ปัดขึ้นให้ผ่าน** โมเดลถูก promote ทั้งที่ตก 2 ใน 3 เกณฑ์
เพราะ UAT ต้องการโมเดลที่มองภาพจริงมากกว่าต้องการโมเดลที่ผ่านเกณฑ์ — เหตุผลเต็มอยู่ใน docstring
ของ `_seed_model_versions` และผลกระทบต่อผู้ทดสอบอยู่ที่ [uat.md §2](uat.md#2--ข้อจำกัดของโมเดล--อ่านก่อนแจ้ง-defect)

**คำอธิบายใต้การ์ดเป็นภาษาไทยที่เขียนไว้ในหน้าจอ** (`GATE_RATIONALES`) ไม่ใช่ `rationale`
ที่มากับ metrics เพราะฝั่ง ML เขียนเป็นอังกฤษสำหรับทีมข้อมูล ส่วน gate ที่หน้าจอไม่รู้จัก
จะ fallback ไปใช้ข้อความของ pipeline แทนที่จะไม่แสดงอะไรเลย

### 4.2 กราฟ "อัตราการตีกลับจากหน้างาน"

**ไม่มีกราฟ drift** โดยตั้งใจ — drift ต้องมี reference distribution ให้เทียบ ซึ่งระบบนี้ไม่ได้เก็บไว้
ตัวเลขที่ไม่มีอะไรอยู่ข้างหลังคือของประดับ · สิ่งที่วัดได้จริงคืออัตราที่พนักงานตีกลับโมเดล
ซึ่งขยับด้วยเหตุผลเดียวกับที่ drift จะขยับ และทุกจุดตามกลับไปหาแถวใน `gap_findings` ได้

```sql
date_trunc('week', gap_findings.verified_at) AS bucket,
SUM(verification_status = 'REJECTED') ÷ COUNT(*)   -- เฉพาะแถวที่ verified_at ไม่ null
```

คำนวณสดทุกครั้งที่เรียก ไม่ได้เก็บค่าไว้ · เลือกช่วงเวลาได้ 8 / 12 / 26 สัปดาห์จากปุ่มมุมขวาบน
(API รับ 1–52) · เกณฑ์ที่ยอมรับได้ 10% (เส้นประ) ·
น้อยกว่า 2 สัปดาห์ไม่วาดกราฟ · **API ไม่เคยส่งว่าใครเป็นคนตีกลับ** และหน้าจอเขียนกำกับไว้ว่า
ตัวเลขนี้วัดคุณภาพของโมเดล ไม่ใช่ของคน

### 4.3 ตารางประวัติเวอร์ชัน

ทุกแถวใน `model_versions` · **เวอร์ชันไหน active ตามค่า env `ML_CLIENT`** ไม่ใช่ค่าที่ตั้งไว้ตอน seed
เพราะ env นั้นคือสิ่งที่ตัดสินจริง ๆ ว่า request การอนุมานวิ่งไปที่ไหน (default = `http`)

| `ML_CLIENT` | เวอร์ชันที่ active |
| :-- | :-- |
| `http` (default) | `shelf-product-yolo26l-960` — โมเดลจริงที่ตก 2 เกณฑ์ |
| `mock` | `mock-v1` — ตัวจำลองที่ไม่มี metrics เพราะไม่มีชุดข้อมูลให้วัด |

เวอร์ชัน `seed-history` ที่ใช้สร้างข้อมูลย้อนหลังก็อยู่ในตารางด้วย และตั้งใจไม่ใส่ metrics
เพราะ detection ของมันคือ label เอง คะแนนจะเป็น 1.00 ทุกช่องโดยโครงสร้าง

### 4.4 สถานะของจุดที่เคยไม่ตรง

| เรื่อง | สถานะ |
| :-- | :-- |
| แบนเนอร์แดงบอกว่าโมเดล "ยังไม่ถูกนำขึ้นใช้งานจริง" ทั้งที่ active อยู่ (`ML_CLIENT=http`) | ✅ แก้แล้ว — แบนเนอร์แยกสองกรณี · ถ้าโมเดลที่ตกเกณฑ์คือตัวที่ให้บริการ จะเขียนว่า **"N เกณฑ์ยังไม่ผ่าน — และ X คือโมเดลที่ให้บริการอยู่ตอนนี้"** พร้อมบอกว่าเป็นการตัดสินใจโดยตั้งใจ และผลตรวจทุกรายการมาจากโมเดลตัวนี้ · กรณีที่ยังไม่ถูก promote ใช้ข้อความเดิม |
| การ์ดเกณฑ์ไม่ผูกกับเวอร์ชันที่ active | ✅ แก้แล้ว — เลือกเวอร์ชันที่ active ก่อนเสมอ และถ้าต้องถอยไปใช้เวอร์ชันอื่นจะขึ้นบรรทัดบอกว่าเกณฑ์ด้านล่างไม่ใช่ของโมเดลที่ให้บริการ |
| โมเดลที่ active แต่ตกเกณฑ์ได้ป้ายเขียวอย่างเดียว | ✅ แก้แล้ว — สถานะกับผลประเมินเป็นคนละป้าย แสดงพร้อมกันได้ ("ใช้งานอยู่" + "ไม่ผ่านเกณฑ์") |
| `mlClient` แสดงเป็น `http` / `mock` ดิบ ๆ | ✅ แก้แล้ว — แปลเป็น "โมเดลจริง (http)" / "จำลอง (mock)" |
| `weeks=12` ตายตัว | ✅ แก้แล้ว — มีปุ่มเลือก 8 / 12 / 26 สัปดาห์ และปุ่มยังอยู่ระหว่างโหลด ไม่หายไปพร้อมเนื้อหา |

## 5. W6 — คิวตรวจภาพเพื่อปรับปรุงโมเดล (`/w/relabel`)

[`app/w/relabel/page.tsx`](../frontend/src/app/w/relabel/page.tsx) ·
`GET /v1/model/relabel-queue?limit=60`

### 5.1 ภาพเข้าคิวได้ยังไง

```sql
WHERE verification_status = 'REJECTED'          -- พนักงานกด "ไม่ใช่"
   OR (is_low_confidence = true                 -- โมเดลได้คะแนน 0.35–0.55
       AND verification_status = 'PENDING')     -- และยังไม่มีใครตอบ
ORDER BY created_at DESC
```

`is_low_confidence` ติดตอนวิเคราะห์ภาพ จาก `low_confidence_threshold = 0.55`
([osa.md ขั้น 1](osa.md#ขั้น-1--กรองด้วย-confidence)) — เป็นค่าเดียวกับที่ทำให้กรอบบนภาพเป็นเส้นประ
ในแอปมือถือ

**เงื่อนไข `PENDING` คือสิ่งที่ทำให้คิวมีจุดจบ** finding ที่โมเดลไม่มั่นใจแต่พนักงาน
ยืนยันไปแล้วว่าเป็นช่องว่างจริง (`CONFIRMED`) ถือว่ามีคนตอบคำถามนั้นแล้วตั้งแต่ยืนอยู่หน้าชั้นวาง
จึงออกจากคิว — มันยังเป็นข้อมูลเทรนอยู่ (label อยู่ในตาราง `gap_findings` และรอบเทรนอ่านจากที่นั่น)
แต่ไม่ได้รอใครมาตรวจ · ส่วน finding ที่ถูก **ตีกลับ** อยู่ต่อเสมอ เพราะการตีกลับคือความไม่ตรงกัน
ที่คิวนี้ตั้งขึ้นมาเพื่อเก็บ

### 5.2 แต่ละการ์ดมาจากไหน

| สิ่งที่เห็น | ที่มา |
| :-- | :-- |
| **ภาพครอบ** | presigned GET URL ของ `captures.object_key` จาก object storage แล้วผ่าน `resolveStorageUrl()` ซึ่งตัด `http://localhost:9000` ทิ้งให้เป็น path สัมพัทธ์ตอน dev |

| "เหตุผล: …" | `rejected_reason` แปลไทยด้วย `REJECT_REASON_LABELS` (มีของแต่ถูกบัง / ไม่ใช่สินค้าของเรา / เป็นพื้นที่ว่างปกติ / อื่น ๆ) |

**⛔ ไม่มีชื่อผู้ตีกลับที่ไหนเลย** — `verified_by` จงใจไม่ถูก select และมีเทสต์เฝ้าอยู่
เหตุผล: คิวที่บอกว่าใครตีกลับคือคะแนนความแม่นรายคนโดยอ้อม แล้วพนักงานที่รู้ว่าการตีกลับถูกนับ
จะเลิกตีกลับ ซึ่งทำลายสัญญาณที่คิวนี้ตั้งขึ้นมาเพื่อเก็บพอดี

### 5.3 กดอะไรได้บ้าง

| ปุ่ม / การกระทำ | เกิดอะไรขึ้นจริง |
| :-- | :-- |
| ฟิลเตอร์ ทั้งหมด / ถูกตีกลับ / ความมั่นใจต่ำ | กรองในหน้าจอ (ข้อมูลโหลดมาครั้งเดียว) ทำงานจริง |
| เช็คบ็อกซ์บนการ์ด | เลือกได้จริง มีแถบสรุปเลื่อนขึ้นมาด้านล่าง |
| "ล้างที่เลือก" | ทำงานจริง |
| **"ทำเครื่องหมายว่าตรวจแล้ว"** | **ซ่อนการ์ดที่เลือกออกจากหน้าจอเท่านั้น** ไม่มี API ไม่มีการบันทึก รีเฟรชแล้วกลับมาครบ (แถบด้านล่างเขียนบอกไว้) |

### ที่ยังเหลือ — ตั้งใจไม่แก้ในรอบนี้

| เรื่อง | ทำไม |
| :-- | :-- |
| **แผนเส้นทางยังไปไม่ถึงมือถือ** (§3.4) | ต้องมีตารางเก็บแผน + endpoint + การตัดสินใจว่าแผนที่อนุมัติแล้วมีอำนาจเหนือการจัดลำดับตามความเสี่ยงแค่ไหน เป็นงานออกแบบระบบ ไม่ใช่การแก้หน้าจอ · ตอนนี้หน้าจอเขียนบอกไว้ตรง ๆ แล้วว่าไม่ถูกบันทึก |

| ปุ่ม "ส่งออกรายงาน" บน W1 | ยังไม่มี endpoint · disabled พร้อมป้าย "เร็ว ๆ นี้" |
| W6 ไม่มีการแบ่งหน้า และ API ไม่บอกจำนวนทั้งหมด | ต้องเพิ่มฟิลด์ในสัญญาของ API |
| ชิป delta ของ KPI ที่ไม่ใช่ % ไม่มีหน่วย | เล็ก และไม่ทำให้ใครอ่านผิดในทางที่อันตราย |
| ค่าเฉลี่ย OSA ถ่วงน้ำหนักตามภาพ ไม่ใช่ตามร้าน | เป็นนิยามของ KPI ไม่ใช่บั๊ก — ถ้าจะเปลี่ยนต้องเปลี่ยนทั้งกราฟและการ์ดพร้อมกัน และเป็นการตัดสินใจของ trade marketing |
